# SPEC: US-002 — Health Check Endpoint

---

## 1. [M] User Story

**As a** operador de Kubernetes,
**I want** un endpoint `GET /health` que confirme que el proceso de la API está vivo y devuelva únicamente `{"status": "ok"}`,
**so that** el monitor de Kubernetes pueda decidir si mantiene esta instancia en servicio.

**Bounded context:** `api` (reference: `docs/context/api.md`)

**Stack:** Python 3.12 + FastAPI (API HTTP JSON existente según el contexto `api`).

**Explicit out of scope:**
- Métricas de CPU, memoria o disco.
- Verificación de dependencias externas (DB, Cache).
- Cualquier dato de salud adicional: el contrato expone solo `{"status": "ok"}`.
- Verbos HTTP distintos de `GET`, `POST`, `PUT`, `DELETE` y `PATCH` (p. ej. `OPTIONS`, `HEAD`, `TRACE`, `CONNECT`).
- Estados transitorios de arranque y apagado del proceso: la historia cubre solo el proceso en servicio.

> `"ok"` significa **el proceso responde**; no afirma que sus dependencias estén sanas.
> Kubernetes permite configurar `method` en un probe `httpGet`; esta historia define el contrato
> solo para `GET` y deja `HEAD` deliberadamente fuera de alcance.

## 2. [M] Acceptance Criteria

| ID | Given (context) | When (action) | Then (observable result) |
|----|-----------------|---------------|--------------------------|
| AC-1 | El proceso está en servicio y acepta peticiones HTTP | Se realiza `GET /health` | HTTP 200, `Content-Type` cuyo tipo de medio es `application/json` (cualquier parámetro adicional, p. ej. `charset`, es irrelevante) y cuerpo **exactamente** `{"status": "ok"}`, sin claves adicionales |
| AC-2 | El proceso está en servicio y acepta peticiones HTTP | Se realiza `POST /health` | HTTP 405, `Content-Type` cuyo tipo de medio es `application/json` (cualquier parámetro adicional es irrelevante) y cuerpo **exactamente** `{"detail": "Method Not Allowed"}` |
| AC-3 | El proceso está en servicio y acepta peticiones HTTP | Se realiza `PUT`, `DELETE` o `PATCH /health` | HTTP 405 con el mismo tipo de medio y el mismo cuerpo que AC-2 (un caso por verbo) |

## 3. [M] Interface Contracts

### 3.1 Input contract

```
GET /health
```

Payload / parameters:
```
N/A — sin query params, sin cuerpo de entrada.
```

Responses:
```
200: application/json — {"status": "ok"}                       (claves exactas; ningún campo adicional)
405: application/json — {"detail": "Method Not Allowed"}        (respuesta estándar para verbos no permitidos)
```

> Contrato cerrado: los únicos verbos en alcance son `GET` (200) y `POST`, `PUT`, `DELETE`, `PATCH` (405).
> Cualquier otro verbo no está definido por esta historia.
> El tipo de medio es `application/json`; si la implementación añade parámetros (p. ej. `charset=utf-8`),
> el tipo de medio sigue siendo `application/json` y el parámetro es irrelevante.

### 3.2 Output contract / side effects

- N/A — sin persistencia, sin emisiones y sin efectos observables.
